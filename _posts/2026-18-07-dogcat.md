## Path Traversal Attack
Việc web có bị **Path Traversal** hay không thì vẫn chỉ là suy đoán thôi. Để chứng minh đuợc thì `fuzz` thôi.

Thử truớc dấu `'` xem có bung lỗi không thì chả có gì xuất hiện cả!!!
Xem lại dấu hiệu ban đầu thì giá trị truyền vào tham số `view` chỉ vọn vẹn là **dog** hoặc **cat** chứ không có extension đi kèm (cụ thể là `.php`). Vậy có thể trong code chúng đang được nối chuỗi với extension => Để đảm bảo suy đoán của mình là đúng thì mình sẽ thử truyền thêm extension cho nó xem có bung lỗi hay không. Mình truyền vào `dog.php` thì thấy lỗi như sau:

![Screenshot](/assets/tryhackme/Screenshot 2026-07-19 at 00.56.31.png)

⟹ Đúng như suy đoán. Thôi đọc code của từng file **dog**, **cat** và **index** thôi nào.
Mình sẽ sử dụng command dưới đây để xem code **php** của chúng.

```
php://filter/convert.base64-encode/resource=dog
```

*Két quả **cat**:* `PGltZyBzcmM9ImNhdHMvPD9waHAgZWNobyByYW5kKDEsIDEwKTsgPz4uanBnIiAvPg0K`

## Path Traversal to RCE
Path Traversal nói chung và LFI nói riêng chỉ giúp chúng ta đọc được file trên server thôi. Vậy phải làm sao để thực thi được lệnh trên server nhỉ. Minh liền nghĩ đến một bug kinh điển một thời là **Log Poisoning**.

### Log Poisoning Attack
Giải thích một chút về lỗ hổng này nhé. Cơ bản thì lỗ hổng này xảy ra khi việc ghi nội dung vào log chưa được filter đúng cách. Trong trường hợp này các access log sẽ ghi gần như toàn bộ nội dung của request header vào log. Cụ thể là các trường như endpoint, User-Agent, ... sẽ được ghi vào access log phía web server. Nếu đặt giả thuyết là, chúng ta sẽ ghi nội dung là một mã php vào access log rồi sau đó lợi dụng lỗ hổng **Path Traversal** để đọc file access log trên server thì liệu mã php đó có thực thi được hay không ?

Để chứng minh giả thuyết này mình sẽ ghi thử một mã php có thể thực thi lệnh ở phía system server như sau: `<?php system('ls'); ?>`. Với mã php này nếu thực thi thành công thì web server sẽ list ra các thư mục/tệp tin đang có ở đuờng dẫn hiện tại trên file access log.
